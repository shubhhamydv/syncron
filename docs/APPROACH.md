# Technical Approach Note: Smart Roster Management System

## 1. Problem Framing
Managing support staff rosters across multiple client brands involves two competing requirements:
1. **Brand SLA Governance**: Each client brand maintains its own operating calendar (e.g. 7-day operations, Mon–Sat, or weekday-only), public holiday closure policies, and minimum staffing thresholds per business process (CS, NDR, Retention, ACC).
2. **Employee Availability Constraints**: Employees operate under pod hierarchies with contractual weekly off schedules, approved leaves, and comp-offs. In single-resource brands (80% of client accounts), a single employee's absence causes an immediate operational gap unless a qualified cross-brand replacement is assigned.

The core challenge was building a system that avoids merging the brand calendar with the employee calendar, detects coverage gaps deterministically, and allows managers to resolve conflicts fairly without violating qualifications.

---

## 2. Key Design Decisions & Trade-Offs

### A. Pure TypeScript Scheduling Engine (No I/O)
- **Decision**: The generator (`generateRoster`) and validator (`validateRoster`) contain zero Prisma queries, zero Express dependencies, and no system clock calls (`Date.now()`). All dates are normalized to UTC midnight string representations (`YYYY-MM-DD`).
- **Trade-off**: Requires an explicit loader (`loader.ts`) to gather database state into an in-memory `EngineInput` object. The benefit is instant, fully deterministic testability without database mocking.

### B. Independent Validator Architecture
- **Decision**: The validator does not consume or trust the conflicts generated by the scheduling engine. It accepts `EngineInput` and raw `RosterEntryDraft[]`, independently re-resolves daily requirements, inspects shifts, and asserts invariants.
- **Trade-off**: Slight redundant CPU cycles during validation, but provides a crucial safety net that catches generator bugs and illegal manual mutations.

### C. Single Soft Rule: Workload Balancing
- **Decision**: When multiple qualified employees are eligible to cover a shift, the scheduler selects the candidate with the fewest assigned working shifts in the month so far. Workload balancing is the only soft constraint; tie-breaking is strictly deterministic by employee ID.
- **Trade-off**: Simple and predictable, avoiding opaque weights or heuristic solvers.

### D. Strict Database Isolation for Tests
- **Decision**: A startup safety check (`assertTestDatabase`) halts test execution unless `DATABASE_URL` targets a database whose name ends in `_test` (e.g., `roster_db_test`).
- **Trade-off**: Requires creating a dedicated `roster_db_test` schema/database locally, but prevents test mutations from touching demo data.

## 3. What Broke and How It Was Found

### 1. The Indus Techworks Duplicate & Missing Conflict Bug
- **Symptom**: On Dec 15, Indus Techworks Retention produced both a `COVERAGE_GAP` and an `INSUFFICIENT_STAFF` conflict simultaneously. On Dec 29, the Tuesday weekly off shortage was missed entirely.
- **Discovery**: Detected through the independent validator's invariant check, which asserted that at most one conflict should ever exist per `(date, brandId, processId)`.
- **Root Cause**: `resolveDailyRequirements` was returning duplicate requirement records for the same brand/process because date-specific and default rules were both pushed without key-based deduplication.
- **Resolution**: Implemented `resolvedMap` keyed by `${rule.brandId}_${rule.processId}` ensuring date-specific overrides weekday-specific, which overrides default. Added tests 14, 15, and 16 in `engine.test.ts` to lock this behavior.

### 2. Toast Count Payload Mismatch
- **Symptom**: After adding approved leave, the UI showed `"Roster is in sync (0 new conflicts)"` instead of `"1 conflict opened, 0 resolved"`.
- **Discovery**: Found empirically during Playwright end-to-end execution.
- **Root Cause**: `syncConflicts` returned `{ opened: number, resolved: number }`, but `ToastContext.tsx` checked `Array.isArray(result.openedConflicts)`.
- **Resolution**: Updated `ToastContext.tsx` to handle numeric `opened` and `resolved` properties from mutation results.

## 4. What I'd Do Next

1. **Intra-Day Shift Granularity**: Transition from whole-day allocations to discrete shift blocks (e.g. 8-hour morning, afternoon, and night shifts) with rest period constraints (minimum 12 hours between shifts).
2. **Employee Self-Service & Shift Swaps**: Introduce a peer-to-peer shift swap workflow allowing employees to propose swaps with automated validation of qualifications before manager approval.
3. **Role-Based Authentication (RBAC)**: Secure routes with JWT authentication separating employee read-only views, pod lead management views, and system administrator controls.
4. **Demand-Driven Dynamic Staffing**: Integrate ticketing volume forecasts to dynamically adjust `minimumStaff` based on historical seasonality.
